## 1. Failles logiques potentielles

### Sévérité haute

- [x] **Fête fixe perdue en fin d'année liturgique** — `lib/calendar_management/location_loader.dart:150`, `lib/classes/location_class.dart:127` (+ copie morte `lib/classes/calendar_class.dart:135`)
  `feastDate.isBefore(endYear)` avec `endYear` = Christ-Roi + 6 jours (dernier jour réel de l'année liturgique) exclut cette date exacte par un test strict. Toute fête fixe romaine ou locale tombant le dernier samedi avant l'Avent est silencieusement absente du calendrier, chaque année.
  → Corrigé le 2026-09-04 (commit `5eeb2532`) : les deux sites actifs remplacent `isBefore(endYear)` par `!isAfter(endYear)`. La copie morte de `calendar_class.dart:135` reste à traiter avec le nettoyage de duplication (section 2).

- [x] **Baptême du Christ mal calculé (Épiphanie "day" un dimanche 6 janvier)** — `lib/calendar_management/common_calendar_definitions.dart:33-36`
  La garde `epiphanyDate.day >= 7` ne couvre pas le cas day==6-et-dimanche → mauvaise branche choisie → Baptême décalé d'une semaine complète (ex. 2019).
  → Corrigé le 2026-09-04 (commit `59023a07`) : la garde devient `epiphanyDate.isSunday && epiphanyDate.day >= 6`, couvrant uniformément les deux modes d'Épiphanie.

- [x] **Transfert Annonciation/Saint-Joseph raté si la date tombe exactement le Dimanche des Rameaux** — `lib/calendar_management/common_calendar_definitions.dart:64,78`

  → Corrigé le 2026-09-04 (commit `1001dc41`) : `isAfter(Rameaux)` remplacé par `!isBefore(Rameaux)` dans les deux fonctions, incluant le Dimanche des Rameaux lui-même dans la branche Semaine Sainte.

- [x] **Copie morte et obsolète du chargeur hiérarchique, exportée dans l'API publique** — `lib/tools/data_loader.dart:56-129`, exporté via `lib/offline_liturgy.dart:8`

  → Corrigé le 2026-09-04 (commit `ef259697`) : `data_loader.dart` réduit à `DataLoader`/`FileSystemDataLoader` seuls ; `offline_liturgy.dart` exporte désormais `hierarchical_common_loader.dart` (implémentation correcte, avec le variant Messes en plus). `dart analyze` propre sur tout le package.

## 3. Pistes d'optimisation de performance

- [x] **`detectCelebrations()` sans mémoïsation** — `lib/offices/office_detection.dart:75-321` — appelé indépendamment par Laudes, Lectures, Vêpres (×2 jour+veille), Complies (×2) ; chaque appel relit et re-parse tous les YAML candidats depuis le disque (`Future.wait(loadFutures)`, lignes 149-168). Point chaud le plus net de l'audit.
  → Corrigé le 2026-09-04 (commit `ddd83b54`) : mémoïsé par clé `(calendar, dataLoader, date)`. Mesuré sur la sonde 60 jours (avec le cache disque déjà en place) : 360 appels pour 61 dates distinctes, 593 ms cumulées → 133 ms après correctif (~4,5×). Note : la partie "relit... depuis le disque" de la description initiale ne s'applique plus telle quelle depuis le fix `FileSystemDataLoader` ; le gain restant vient du reste du travail de la fonction (tri, résolution des titres de commun, etc.), pas de l'I/O.
  → Affiné le 2026-09-04 (commit `03e6cef6`) : la clé incluait `dataLoader`, ce qui — même défaut que les caches de bibliothèques — annule le gain dans aelf-flutter (nouvelle instance par appel). Clé réduite à `(calendar, date)` : `offlineCalendar` est réutilisé de façon stable côté app (reconstruit seulement au changement de région), donc ce gain-là profite réellement à l'app, contrairement au cache disque `FileSystemDataLoader` (voir remarque ci-dessus, jamais parcouru par aelf-flutter qui a son propre `FlutterDataLoader` non caché, dans un autre dépôt).
- [x] `bestPrecedence` recalculé **dans** la boucle par célébration au lieu d'être sorti une fois (contrairement à `hasHighPriority`, correctement hissé) — `office_detection.dart:250-251` — O(n²) évitable.
  → Corrigé le 2026-09-04 (commit `8df8283e`) : calcul hissé avant la boucle, juste après `hasHighPriority`. Formule inchangée (précédence brute, pas `.first` après tri qui utilise `effectivePrecedence` et diverge sur certains cas férial/mémoire facultative).
- [x] **Chargement des "commons" hiérarchiques non caché** — `lib/tools/hierarchical_common_loader.dart:71-108` — les 4 fonctions `loadXHierarchicalCommon` re-parsent indépendamment le même fichier YAML physique (ex. `commons/martyrs.yaml`) une fois par type d'office, jusqu'à 4× pour un seul jour.
  → Évalué le 2026-09-04, non retenu : le coût CPU (parsing YAML) est déjà couvert par la mesure de l'item `convert_yaml_to_dart.dart` (négligeable, 73 ms). Le coût I/O éventuel passe par `dataLoader.loadYaml`, qui pour aelf-flutter utilise `FlutterDataLoader` (autre dépôt, non caché, hors de portée d'ici) — impossible à mesurer ou corriger depuis ce paquet sans données de profilage sur un vrai appareil. Si ça s'avère un jour nécessaire, le bon endroit est un cache dans `FlutterDataLoader` lui-même (bénéficierait à tout, pas seulement aux commons), pas un cache sémantique ad hoc ici.
- [x] Le pipeline Messes charge le commun hiérarchique **deux fois** pour la même célébration — une fois en détection (juste pour un flag booléen `hasFeastReadingParts`), une fois en export — `mass_detection.dart:53`, `mass_export.dart:70`. Seul des 5 pipelines à le faire.
  → Examiné le 2026-09-04, non retenu : correctif possible identifié (transporter le `Masses` déjà chargé en détection via un nouveau champ `CelebrationContext.commonMasses`, réutilisé par `massExport` avec repli sur le chargement normal si absent — même précédent que `hasFeastReadingParts`/`massName`). Écarté car il demande un import circulaire entre `office_elements_class.dart` et `mass_class.dart`, et un champ spécifique aux Messes sur une classe partagée par les 5 offices, pour un gain limité au seul chemin détection→export via le même contexte. Même logique de retenue que l'item général "commons hiérarchiques non caché" ci-dessus.
- [~] Caches des bibliothèques ne mémorisent que les succès, jamais les échecs — `psalms_library.dart:50-67`, `hymns_library.dart:32-49`, `prefaces_library.dart:11-29`, `eucharistic_prayer_communicantes_library.dart:13-36` — une recherche sans résultat relance systématiquement le chargement.

## Priorisation suggérée

1. **Bug de sélection de Messe** (Noël/Rameaux/Vigile pascale) — impact utilisateur direct sur des jours à forte fréquentation.
2. **Bugs de dates calendaires** (fête perdue fin d'année, Baptême du Christ, Annonciation/Saint-Joseph) — rares mais silencieux, difficiles à détecter sans audit ciblé par année.
3. **Antienne pascale manquante à Complies** — visible chaque année pendant tout le Temps Pascal.
4. **Nettoyage de `data_loader.dart`** — pas un bug actif, mais exporté publiquement ; simple à corriger et évite un piège futur pour les consommateurs du package.
5. Le reste (schémas généraux, perf) peut être traité au fil de l'eau, sans urgence — aucun point de performance identifié n'est bloquant à l'échelle actuelle des données.
